| R-033 | Stage 2 access control (DL-059) is stored but not used: no endpoint checks it, no admin API or bootstrap command exists, and the API still authorizes any signed-in user. People are bare `sub` values with no directory, so a typo assigns a role to nobody, and a reused `sub` would inherit roles. Limits are provisional. Every call reads the whole model (no cache, by design, DL-059f), so cost grows with assignments. The schema owner can drop the triggers (as R-026), and the app login has DML on the current-state tables, so a forged role row is not prevented; since DL-060 a plain edit is detected on the next read (model hash and version link) and audited, and every access check then fails closed until repaired (runbook ACCESS_CONTROL_INTEGRITY). The hash is not keyed, so someone holding the module login can forge a matching version chain and grant a role undetected (DL-061a: keyed hash from the vault, P0-013b, before production). A release that changes the hash format, removes an action or adds a conflicting pair locks deployments out unless it ships a re-hash migration (DL-061c). Integrity audit events are limited to one per step, check and request per minute per process; the count left out is recorded. Rate limits are per process, so several API instances multiply them until a shared store is used. The bootstrap needs a dedicated short-lived login and an approval reference (DL-063a), but whoever can create database logins can still run it first: the alert and second-person confirmation make that visible, not impossible. The tool's success path is tested through the service, not end to end. `POST /changes` has no idempotency key.
